表现：拖动、缩放均有明显滞后感；但页面自报的绘制耗时 < 10ms。

## 二、那条"骗人"的指标

`performance.now()` 包住绘制调用，量到的是 **Canvas2D 指令提交时间**。
光栅化是异步的，真正的像素填充发生在之后——所以计数器永远显示得很漂亮。

**任何"绘制耗时"指标都必须和真实帧间隔对照**，否则没有意义。

本轮后期加了常驻 rAF 探针，测相邻帧的真实间隔：

```
缩放 9%  ·  帧 16ms  ·  绘 3.2ms
```

## 三、对照实验（关键一步）

做了一张 `帧率对照.html`：同样尺寸的画布、同样 4550×4254 的大位图，
拖动/缩放时**只做一次 drawImage**，不含任何地图逻辑。

结果：**对照页非常顺，舆图卡。**

结论：不是显卡、不是远程桌面、不是软件光栅——
是舆图自己的绘制路径有问题，且问题是这几轮改动引入的。

## 四、试过什么，为什么失败

| 改动 | 意图 | 结果 |
|---|---|---|
| 交互时半分辨率画布 | 填充像素降到 36% | 改 `canvas.width` 会重分配后备缓冲，**本身几百毫秒卡顿**，反而更糟 |
| 交互时"廉价重绘"（简笔描边） | 省掉离屏合成 | 观感极差，"太廉价" |
| 整幅底图 0.5 倍直贴 | 一次 blit 覆盖全图 | 需临时改全局 `ctx/cw/ch`，污染主画布，出现"页面重复渲染" |
| 独立 `renderBaseMap()`（不碰全局） | 同上但干净 | 生成成功，但**每帧两次全屏 blit**（底图 + 快照），实际更慢 |
| 底图降到 0.25 倍 | 减小源图 | 填充成本由**目标矩形**决定，源图变小无济于事 |
| 条带裁剪（只在快照没盖住处补底图） | 减少填充面积 | 逻辑正确，但与上面几项叠加后整体仍未改善 |
| 空闲预抓快照 | 手势开始零成本 | 有效，但抵不过上面的开销 |
| `touch-action:none` | 消除浏览器手势判定延迟 | 该加（正确性修复），但不是本次卡顿的主因 |

### 根本教训

**多个"优化"叠加时会互相抵消，而且很难归因。**
这一轮同时改了渲染路径、分辨率、缓冲策略，任何单点都可能是瓶颈，
最后只能整体回退。

回退后的实现（当前在用）：

2. 交互时：桌面 → 底衬 → 当前视野快照 → 停手 260ms 后完整重绘
3. 底衬只生成一次，图层开关变化时才重算

## 六、下次重来的正确顺序

不要一次上多项。每步单独验证，用对照页式的做法。

1. **先测**：`帧 16ms / 绘 X ms` 两个数都要，拖动与缩放分开测
2. **一次只改一处**，改完立刻用同一组动作复测
3. 候选方向（按预期收益）：

| 方向 | 说明 | 风险 |
|---|---|---|
| 分块渲染 | 512×512、0.5 倍的瓦片，惰性生成 + LRU，交互只贴可见块 | 实现量大，但内存可控、任意缩放连续 |
| 把 `draw()` 拆成纯函数 | `drawScene(target, view)` 不碰全局、不动 DOM | 是所有底图/瓦片方案的前提 |
| 静态层合并 | 纸面+水系+海岸+城邑合成一张，交互时只重画疆域 | 疆域改动时才失效 |
| 减少渐变开销 | 内侧渐变按国家缓存（已做），进一步按"屏幕分块"缓存 | 需要稳定的变换 key |

4. **不要动 `canvas.width`** 做分辨率切换——重分配是硬卡顿
5. 每帧填充面积比源图分辨率更重要：**目标矩形越小越快**

## 七、一句话

优化前先测量，测量要测**真实帧间隔**；
一次只动一处；对照页比任何解释都有说服力。

### 9.0 失败结论（症状细节待用户补充）

用户实测后直接判定"完全是负面优化"。在弄清具体症状前，**不要重试同类改法**。

### 9.1 当时数出来的热点（数对了，改错了）

| # | 热点 | 原状 |
|---|---|---|
| 1 | `fillPatch` 每疆域一次**全屏**离屏 clear+fill+blit | 289 疆域 = 289 次全屏合成/帧 |
| 2 | drawBg 每帧重建静态几何 Path2D | 海面环 2354 点路径逐帧构建 |
| 3 | faces/edges 每帧重建 Path2D | computeFaces 产物是对象数组，可按对象缓存 |
| 4 | `realms.slice().sort()` 每帧 | 289 项排序/帧 |
| 5 | 平移/缩放无快照，且交互事件同步触发 draw | 无 rAF 合帧 |

### 9.2 改动（单一提交 `35d5cef`，生成器 + 产物一起）

1. **静态几何缓存**：`_closedP2d`/`_openP2d` WeakMap + `riverPath` 扁平数组 +
   `seaComposite()`（键 = `S.V` 数组身份，setVector 即失效）——海面/海岸/湖泊不再逐帧重建
2. **fillPatch 重写**：无洞疆域直接主画布 `ctx.fill`；有洞疆域走设备包围盒离屏池
   （grow-only `_pcv`，destination-out 挖洞）——热点 #1 从 289 次全屏合成归零
3. **快照平移/缩放**：手势期间位图平移缩放（`takeSnap`/`drawSnap`），自适应回弹
   （全量绘制 <8ms → 140ms，否则 260ms）；顶点拖拽等需新渲染的分支 `endSnap()` 立即回真
4. **rAF 合帧** `requestDraw`；`markMoving` 节流
5. **sortedRealms / natById 缓存**：键 = 数组身份 + 长度（冒烟测试会 `realms.push` /
   `realms.length=0`，身份键自动失效，无需手动清理）
6. **边层世界坐标 `edgePath` 缓存**（`e._p2d`），四处顶点原地变更点显式置空；
   顶点/端点标记拆到独立屏幕坐标循环
7. **draw 计时探针** + 状态栏「缩放 xxx% · 绘 x.xms」实时读数

### 9.3 当时的"验证"为何没拦住

- 冒烟 15 组断言全绿——但冒烟只验**功能正确性**，canvas stub 无法度量真实 GPU 合成开销
- 产物 14 项标记抽查全过——只证明"代码进去了"，不证明"更快"
- **结论：节点冒烟测试对"性能是否变好"零证据力；真浏览器实测是唯一裁判**（§六.1
  在舆图上学过的教训，搬到编辑器时又没执行到位——改完应先自测手感再交付）

### 9.4 可能的失败原因（[待验证]——需用户症状描述才能收敛）

- [待验证] fillPatch 无洞直填改变了**填充顺序/混合方式**：旧版每疆域独立离屏再 blit，
  新版直接在主画布叠 fill——若图层间有半透明依赖，视觉即错
- [待验证] 快照手势期间的位图缩放模糊/错位感，可能被用户感知为"变卡/变糊"
- [待验证] 某处缓存失效遗漏 → 拖顶点后画面不更新或残留
- [待验证] grow-only 离屏池在高分屏下的内存/分配抖动

### 9.5 教训（比舆图轮多一条）

舆图轮的方法论（数热点→小步改→冒烟）在**只读数据**上成立；编辑器是**可变数据 +
高频写路径**，对象级缓存的失效点分散在交互代码各处，静态冒烟覆盖不了。
下次动编辑器渲染：改一步 → 自己在真浏览器里拖一轮 → 再改下一步。
