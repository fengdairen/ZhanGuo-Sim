## 1. 官方技术口径 `[已证实]`

来源：Google Cloud 客户案例《当 Gemini 3 成为〈历史模拟器：崇祯〉的世界引擎》。

### 1.1 定位：模型不是 NPC，是"世界模型"

> "没有既定结局，没有僵化的'如果 A 则 B'。玩家的每一个决策，都将由模型实时解析。"

他们把大模型放在**游戏世界的底层引擎**位置，而不是对话框里。

### 1.2 核心链路（原文）

> 它要在瞬间完成"**意图解析 → 逻辑推演 → 数据更新与文本反馈**"的复杂闭环。
> "将这些决策合理化推断，转化为国库银两的增减、边关战力的起伏、甚至朝堂党派的态度变化，并精准修改底层数据。"
> "Gemini 3 会输出准确的**函数调用**，精准地更新国库、派系、军队等核心数据。"

**关键判读：**
- 走的是 **function calling / 结构化工具调用**，不是让模型吐一段自由 JSON 再 parse。
- "数据更新"和"文本反馈"是**同一个闭环的两个产物**。
- 状态规模：官方说"数千个维度的数据"。

### 1.3 上下文策略：硬扛

> "在实测中，单次游玩的 Token 消耗量达到了惊人的 **3000 万级别**！"
> "通过与团队深度合作，通过一系列创新方式突破了上下文的硬限制。"

`[推测]` "创新方式"大概率是：分段摘要 + 关键状态外置 + 检索注入。但官方没有公开细节。
`[判读]` 这条路**成本极高且仍然会漂移**，不是可复制的技术路线。

### 1.4 三大自述挑战（等于自曝弱点）

官方自己列了三个难点：

1. **规则爆炸** — 传统代码树写不完，所以交给模型。
2. **上下文记忆管理** — 长局会忘。
3. **复杂指令执行** — 玩家一句话里可能嵌套 5 个动作。

这三条，恰好对应我们后面要设计的三个模块。

## 2. 补丁日志：一份免费的"事故数据库" `[已证实]`

来源：0.5.0–0.5.6 更新报告（2026-10 官方发布，17173 转载）。

### 2.1 架构层面的改动（比 bug 更值得看）

| 版本 | 改动 | 我的判读 |
|---|---|---|
| 0.5.0 | 优化奏对、廷议的**缓存复用** | 长对话的成本控制，说明他们在做 prompt caching / 结果复用 |
| 0.5.1 | **内阁票拟改为本地处理** | 票拟这种规则性强的环节，从"调模型"降级为"本地代码/小模型"——降本 + 提稳定 |
| 0.5.2 | **默认启用本地判官** | 同上：把"判定"从云端大模型挪到本地。这是最重要的一条 |
| 0.5.3 | 新增**本地语音输入** | 输入层本地化 |
| 0.5.6 | 道具面板分页；**修复读档误清算库银** | 存档/读档与状态机不一致 |

**趋势判读 `[推测]`：**
他们在把**判定（judge）**从"大模型自由裁量"逐步迁移到"本地确定性组件"。
趋势很清楚：**能确定性算的，绝不该交给模型。**

### 2.2 Bug 清单 → 六类失效模式

把 0.5.1–0.5.6 的所有修复条目归类，得到一张非常有用的"踩坑地图"：

| 类别 | 具体 bug | 本质问题 |
|---|---|---|
| **A. 实体指代错乱** | 抄错人；归附人物无法召见 | 自然语言 → 实体 id 的绑定不可靠 |
| **B. 幂等缺失/重复执行** | 重复抄家；读档误清算库银 | 同一指令被执行两次，或重放时副作用重放 |
| **C. 状态机不同步** | 下狱后不认诏令；批准处决不执行；罢免/下狱/查案执行异常；差事中断 | 实体的 status 与流程状态脱节 |
| **D. 账目方向错误** | 抄家不入账；**支出误记收入** | 借贷方向错，存量/流量混淆 |
| **E. 队列与生命周期** | 奏疏处理后不消失；定期奏报不延续；新手引导卡住 | 待办队列的"消费"语义缺失 |
| **F. 系统边界混淆** | 派差被误判为官职任命；私聊答非所问 | 意图分类串台 |

这六类，就是我们设计时要**逐条设防**的清单。

### 2.3 特别值得注意的三条

1. **"读档误清算库银"** —— 读档触发了一次结算。说明他们的结算逻辑不是纯函数，**读档/重放不是无副作用的**。这正是事件溯源要解决的问题。
2. **"支出误记收入"** —— 方向性错误。财务报表必须用**带符号的分录**，而不是模型填正数。
3. **"下狱后不认诏令"** —— 实体状态与可执行动作没有联动校验。我们需要"动作的前置条件表"。

## 3. 玩家社区总结的 10 条"元规则" `[已证实]`

一位 MOD 作者的实测总结，信息密度极高，等于把系统内部结构说穿了。摘录与判读：

| # | 玩家结论 | 判读 |
|---|---|---|
| 1 | 大臣对话与诏书推演是两个系统，只有拟旨是桥 | 有意的上下文隔离 |
| 2 | 派系/阶层/装备/兵种/科技写死，改不了一丝一毫 | 枚举型 schema，模型无权扩展 |
| 3 | 大臣/军队/省份建筑是活字段，可改 | 列表型实体，可增删 |
| 4 | 大臣介绍写定，官职每轮调整，官职是文本字段 | 人设与身份解耦；官职是弱类型 |
| 5 | 六部尚书/六殿大学士是写死的坑，加不了减不了；多人挂同一衔容易出错 | 槽位唯一性假设 |
| 6 | 对话第一句写人设效果最好；拟旨过不过关由推演模型决定 | 人设影响对话，不影响判定 |
| 7 | 省份建筑可加 buff 和收入，但**一次建太多推演不认** | 单轮变更幅度有隐含上限 |
| 8 | 可编练新军、调编制、赏赐、补补给；会**影响财政流量** | 军事操作会落账 |
| 9 | 财政必须盯紧；**存量→流量不会自动转换**；改税制要显式调收入字段；AI **没有跨期能力** | 最致命的架构缺陷 |
| 10 | 大臣拟旨爱让你从内帑花钱 | 模型的行为偏好会系统性偏移 |

第 9 条是整份材料的"题眼"：
> "ai 没有能力进行跨期操作" —— 玩家原话。

这意味着：**任何需要跨回合保持一致的计算（摊销、复利、逐年递减、长期工程），都不能交给模型。**

## 4. 他们的方案，抽象成架构图

综合以上，我重建出他们的实现（`[推测]`，与所有证据自洽）：

```
┌─────────────────────────────────────────────────────────┐
│  前端：诏书输入（文本/语音） → 廷议对话                   │
└───────────────────────┬─────────────────────────────────┘
                        ↓  拟旨文本（唯一的跨系统通道）
┌─────────────────────────────────────────────────────────┐
│  世界引擎（云端大模型，Gemini 3）                          │
│   ① 意图解析（读诏书 + 状态快照 + 检索到的历史）            │
│   ② 逻辑推演（在"数千维度"上做因果推断）                    │
│   ③ 输出：叙事文本 + function call 列表                    │
└───────────────────────┬─────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  后端：字段更新（写死枚举 + 活列表 + 财政数值）             │
│  + 本地判官（0.5.2 起默认启用）—— 兜底校验/降本            │
└───────────────────────┬─────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  存档（序列化状态 + 历史）；读档曾被误触发结算（已修）      │
└─────────────────────────────────────────────────────────┘
```

**他们的三个结构性弱点：**

1. **状态是"字段集合"而非"可回放的事件流"** → 读档重算会出错，长局会漂。
2. **更新由模型提议、缺乏强校验** → 支出记成收入、抄家不入账。
3. **跨期计算交给模型** → 摊销、长期工程、慢性恶化全部失真。

这三条，正是我们要建"数据系统"的理由。

## 5. 我们直接吸收 vs 直接规避

### 吸收

- ✅ 诏书 → 意图解析 → 结算 → 奏报 的四段式闭环
- ✅ 对话系统与结算系统物理隔离，只靠"拟旨"文本桥接
- ✅ 写死枚举 + 活实体列表的分层 schema
- ✅ 固定槽位（官职/内阁）且带唯一性约束
- ✅ 用"本地判官"兜底：确定性规则优先于模型
- ✅ 缓存复用（奏报、廷议、重复查询）

### 规避

- ❌ 不靠超长上下文维持记忆 → 用状态快照 + 事件日志 + 定向注入
- ❌ 不让模型直接写字段 → 模型只产出"提议"，后端校验后原子提交
- ❌ 不把跨期计算交给模型 → 账本与摊销是纯函数，按回合确定性推进
- ❌ 不做"一次性大幅变更" → 单轮变更幅度设上限并显式拒绝
- ❌ 不做有副作用的读档 → 结算必须是 `f(state) -> state'` 纯函数

## 6. 一句话总结

> 崇祯团队用"云端大模型 + 函数调用 + 本地判官"跑通了体验，
> 但**没有把状态当作一等公民**。
> 差距不在模型更强，而在于**状态是否被当作一等公民**。
