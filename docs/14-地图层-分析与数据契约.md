### 1.1 最关键的一点

**「城池」与「城池名称」是两个独立图层。**
符号和名字在美术上分开绘制，**没有任何绑定关系**——图上没有 id、没有坐标表、没有属性。

### 1.2 必须注意

- 图例组在图上有定义，但**导出 PNG 中不可见**（该区域像素只有 1 种颜色）。要图例得从 PSD 取。
- 图面深色像素占比约 **2.7%**，包含文字、边界虚线、符号，密度很高。

## 3. 数据契约：地图层要和谁对接

### 3.1 现成的接口

经济表里已经带着地名：

| 表 | 字段 | 鲁国的值 |
|---|---|---|
| 人群表 | 核心城市 | 曲阜 / 费邑 / 郕邑 / 郈邑 / 平陆 |
| 军队表 | 驻地 | 郕邑 |
| 工程开支 | 项目名 | 国都 / 齐长城 / 赵长城 |

这些字符串必须能被地图层解析成节点 id。

> **所以地图层的第一职责不是画图，是提供一份权威地名索引。**

### 3.2 建议结构

```
Node    城邑（都/城/邑）· 关隘 · 渡口
Edge    道路（陆）· 河道（水，可通航）· 险道（山）
Region  国 · 部族 · 郡
Attr    地形 · 资源 · 长城 · 可耕性
```

### 3.3 与经济表的耦合点

| 经济表字段 | 依赖地图的什么 |
|---|---|
| 都/城/邑 数量 | 节点的分级 |
| 产值/税基 | 可耕性、开发度 |
| 军费 | 驻军节点的补给能力 |
| 行军 | 节点间距离（→ 行军日） |
| 赈灾/漕运 | 路径长度与通航性 |

## 4. 从图到数据的三种路径

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | 在 PS 里分层导出透明 PNG：城池 / 城池名称 / 河道湖泊 / 河道名称 / 海岸线 / 部族范围 / 险道 / 长城 / 资源 | 提取是**确定性**的，可校验 | 用户约 10 分钟 |
| B | 用户直接提供城邑清单 CSV（名字 + 位置） | 最快 | 可能没有现成 |
| C | 在合成图上做符号检测 + OCR | 不占用用户时间 | 生僻字必错（郈、郕、鄗、邺） |

### 4.1 为什么 A 明显更好

拿到**只有城池方框**的单层后：

1. 二值化 → 连通域分析 → 筛 bbox 尺寸在 7–16px、近似正方形、内部为空的连通块；
2. 得到每个方框的中心坐标（**几乎不会误检**，因为方框是规则的几何形状，而文字笔画不规则）；
3. 再和「城池名称」层做最近邻配对，或对每个方框右侧裁一小块做 OCR 复核。

这样"位置"是算出来的，"名字"才需要 OCR 或人工——把最贵的部分（定位）变成确定性的。

### 6.3 已知的三类错误

1. **单字地名漏识**——吕、霍、杨、绵、续、温这类单字名，Windows OCR 常常直接跳过。
2. **相邻标签粘连**——密集处两个名字被识别成一行，例如「大梁小黄」「岸门曲沃」「泾阳陵」「灵寿龙」。
3. **生僻字误识**——如 铜鞮 → 铜緹。

`[判读]` OCR 在这类历史地名上已到上限：字库偏现代，生僻字必错。
**要 100% 准确，必须有原始名录。**

## 7.5 重要修正：部族不是点，是面

用户补充：

> "有一些词是没有城的图例的，是因为他们是部族，我在周围用虚线圈起来的，部族没有小方格具体地址，只有虚线圈的大致范围；部族名称并不在城邑名称的图中，但在全图里是有的。"

**因此地图层必须分成两类实体：**

| 类型 | 几何 | 方格 | 名称来源 | 状态 |
|---|---|---|---|---|
| **城邑 Node** | 点 | 有（邑/城/都） | `城池名称.png` | ✅ 已提取 1038 个 |
| **部族 Region** | 面 | 无 | 全图 `ditu.png` | ❌ 待提取 |

`[判读]` **部族名与城邑名在同一张 `城池名称.png` 里**（用户确认）。所以：
- 有对应小方格的词 → 城邑名
- 没有对应方格的词 → 部族名（应归入 Region）

这也解释了"1098 个文字块 vs 1038 个城址"的差额：多出来的约 60 个词，正是**无方格的部族名**（另有少量切分误差）。
→ 部族名单可以直接从"未分配到城址的词"里提取，不必再要新图层。

`[设计含义]`
- **Node** 参与：行军路径、驻军、赋税来源、粮道、攻城
- **Region** 参与：势力范围、游牧活动区、可否穿越、招抚/征伐
- 两者在数据里必须分成两张表：`Region` 用多边形或「中心点 + 半径」描述
