# 50 · 目标游戏拆解：《历史模拟器：崇祯》

> 目的：搞清楚"用户说的那个游戏"到底是什么，它的核心循环、数据模型、以及它刻意制造的难度来自哪里。
> 结论先行：**它不是一个"AI 聊天游戏"，而是一个"用大模型当世界引擎、用结构化字段当真实状态"的策略模拟器。**

---

| 项 | 内容 |
|---|---|
| 名称 | 《历史模拟器：崇祯》 |
| 类型 | AI 原生历史策略游戏（官方口径：国内首款） |
| 开发 | 青干工作室 |

| 发售 | 2026-05-08 |

开局设定：1627 年，16 岁登基。陕西大旱、辽东后金、国库见底、党争不休、小冰河期天灾。

## 2. 核心循环 `[已证实]`

```
    ┌──────────────────────────────────────────────┐
    │                                              │
 看奏折 ──→ 召大臣廷议 / 私聊 ──→ 拟旨（可采纳建言）──→ 颁布诏书
    ↑                                              │
    │                                              ↓
    └──── 奏报回馈（欠饷/民变/城防空虚）←── 推演结算（模型驱动）
```

关键设计：**没有"确认/取消"按钮**。系统不会当场告诉你"这不行"。
命令会先走下去，代价在几回合后以奏折、欠饷、民变、失守的形式回到案头。

这是整个游戏的"爽点"也是"痛点"来源：**延迟反馈 + 资源守恒 + 执行损耗**。

## 3. 两套 AI 系统，一条窄桥 `[已证实]`

这是社区玩家（MOD 作者）总结、并被官方行为印证的最重要结构：

1. **大臣对话系统**（廷议 / 私聊）：每个大臣是独立智能体，有立场、性格、官职认知。
2. **诏书推演系统**：真正结算世界的那套。

**拟旨是唯一的桥。** 玩家在对话里聊过什么，推演系统**完全不知道**；只有写进诏书/拟旨文本的内容，才会进入推演上下文。

> 原文（玩家社区）："大臣对话的拟旨会成为诏书推演的上下文，但大臣对话本身不会，诏书推演不知道你和大臣聊过什么，拟旨里没有就是不存在。"

`[判读]` 这是刻意的"信息损耗"设计：**nl 对话不直接改状态**。对话只产出文本，文本再进入判定。这天然避免了"聊天把世界聊崩"。

## 4. 数据模型（从玩家指南逆推）`[已证实 + 推测]`

社区总结的字段分类，几乎就是一份数据字典：

### 4.1 写死字段（不可增删）

| 字段 | 说明 |
|---|---|
| 派系 | 阉党 / 东林 等，固定枚举 |
| 阶层 | 固定枚举 |
| 装备 | 固定枚举 |
| 兵种 | 固定枚举 |
| 科技 | 固定枚举 |

> 玩家原话："派系、阶层、装备、兵种、科技是写死的字段，改不了一丝一毫，无法添加，无法删除。你当然可以在上下文里加料，但上下文未必记得住。"
>
> `[推测]` 这里的"写死"意思是：**schema 里是枚举，模型不能新增枚举值**；写进上下文的"新兵种"不会变成真数据，下一轮就丢了。

### 4.2 活字段（可增删改）

| 字段 | 说明 |
|---|---|
| 大臣 | 可引入、可罢免、可下狱、可抄家 |
| 军队 | 可编练、可裁撤、可合并、可改名、可调编制 |
| 省份建筑 | 可兴建，提供 buff/减益与杂项收入 |
| 官职 | **纯文本字段**，每轮随诏书调整，参与大臣的"自我角色认知" |

### 4.3 固定坑位

六部尚书 + 六殿大学士是**写死的槽位**，不能加不能减。玩家反馈：让多个官员同时挂尚书衔时，推演容易出错。
`[推测]` 这暗示实现上是"槽位 → 大臣 id"的映射，允许多人挂同一衔会破坏一对一假设。

### 4.4 财政：存量 vs 流量（最要命的部分）

玩家社区里最长的吐槽都在这：

- **存量**：国库余额、内帑余额。
- **流量**：田赋收入、旧饷收入、辽饷收入、杂项收入、其他内帑收入、各项支出。
- 抄家这类操作默认被理解成**存量**扣减；如果要让它变成持续的**流量**，必须在诏书里显式要求修改"杂项收入""其他内帑收入"字段。
- 改税制后，必须显式提醒模型调整田赋/旧饷/辽饷的收入值，否则"税率改了但收入没动"。
- 改王田税率同理：**税率和收入是两套字段，不联动**。

> `[已证实]` 这是玩家实测结论，不是猜测。原文："如果你是动赋税制度，动完之后必须提醒推演模型注意调整田赋、旧饷和辽饷收入。"

`[判读]` **这是财政模型的关键断点**：如果状态是"模型自由写的一段话"，税率和收入就永远对不上。要让二者联动，中间必须有一条**公式边**，而不是指望模型"记得"去改。而崇祯的系统里明显没有这条边。

## 5. 为什么难：四重挤压 `[已证实]`

官方/媒体反复强调的设计意图：

1. **资源守恒**：钱、兵、粮、人手、时间是同一个池子，动一处必伤另一处。
2. **执行损耗**：诏书要经人手实施，办事的人有自己的立场，命令会被打折、被扭曲、被中饱。
3. **时间滞后**：效果延迟数回合出现，且以"问题"的形式回来。
4. **信息不对称**：你不知道真实的库存与忠诚度，只能看奏报（而奏报本身可能失真）。

结果：内测数据称 **97% 的玩家没撑过崇祯五年**。

## 6. 玩家侧的真实体验问题 `[已证实]`

媒体评测与玩家反馈里反复出现的三类问题，恰好是我们必须避免的：

1. **逻辑不一致**：同一件事前后判定矛盾。
2. **长局记忆漂移**：几十回合后，模型"忘了"十年前的政令。
3. **跨期操作无能**：AI 无法做"分期摊销""逐年递减"这类跨回合的一致操作——玩家建议直接回退一回合重推。

> 官方技术口径承认单局 token 消耗达 **3000 万级**，靠长上下文硬扛连贯性。
> `[判读]` 这不是可复制的技术路线：3000 万 token 的代价是成本与延迟，而且即便如此**仍然会漂移**——说明瓶颈不在上下文长度，而在状态载体。

## 7. 结构特征一览

把上面拆出来的东西压缩成一张表，作为后续对照的基线：

| 维度 | 崇祯的做法 | 性质 |
|---|---|---|
| 输入 | 自由文本，无选项按钮，支持语音 | 玩法核心 |
| 子系统性 | 对话 / 拟旨 / 推演，三者靠文本串联 | 架构核心 |
| 跨系统通道 | 只有"拟旨文本"，对话原文不共享 | 刻意的信息瓶颈 |
| 字段分层 | 枚举（写死）/ 实体（活）/ 槽位（固定） | 数据模型核心 |
| 财政 | 存量与流量两套字段，中间无公式 | **主要缺陷** |
| 反馈 | 延迟数回合，以"问题"形式返回 | 张力来源 |
| 记忆 | 超长上下文（3000 万 token/局 + 摘要检索） | 成本与漂移的来源 |
| 校验 | 有"检测层"，强度随难度可调 | 0.5.x 起逐步本地化 |
| 写入 | 模型输出函数调用，直接改字段 | **主要缺陷** |
| 回放 | 弱（读档曾误触发结算） | **主要缺陷** |

## 8. 一句话总结

> 崇祯的成功在于**敢让模型当世界引擎**；它的痛苦在于**没有给这个引擎配一套数据库**。
> 它的每一个长局问题，都能追溯到"状态没有被当作一等公民"。
