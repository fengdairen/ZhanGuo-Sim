# 19 · 定性状态层：LLM 读什么，代码管什么

> 起因：用户 2026-11-11 的判断——
> **"定性内容很重要。其实 LLM 对于数值是没有实感的，这种定性描述反而有助于它推演。"**
>
> 这条判断改变了我们对"LLM 该看到什么"的设计。本文把它落成可执行的形态。

---

## 一、问题的本质

我们原来的假设是：状态 = 数值树，LLM 读数值、输出系数。

**这是错的。** LLM 拿到 `粮: 400, 需求: 700` 只会做算术，而做算术是代码的活；
它真正擅长的是理解 "**四百块巨款 vs 中山军团一年要吃七百**" 这种**带评价的对照**。

而人类 GM 的真实工作方式（`docs/18` 那份记录）恰恰是：

> "魏侯调来的粮食，不能说杯水车薪吧，也可以说是聊胜于无了。"

这句话里没有精确数字，但**信息量远大于一个 400/700 的比值**——它同时传达了：
数量级差距、执行者的自我感动、旁观者的评价、后续推断（"灵寿也吃不饱"）。

**结论：数值是账本，定性是模型的工作介质。**

---

## 二、三层分工

| 层 | 内容 | 谁写 | 谁读 |
|---|---|---|---|
| **真值层** | 人口、粮、钱、兵、税基、制度等级 | **只有代码** | 代码；以及生成定性层时读 |
| **定性层** | 国情卡、势力卡、事件卡、征兆 | **由真值派生**（模板 + LLM 润色） | **LLM 判定时只读这一层** |
| **奏报层** | 给玩家看的叙述 | LLM 写，代码校验数字锚点 | 玩家 |

关键规则：

> **LLM 永远不直接读裸数值表；它读的是"由数值投影出来的定性卡"。**
> 定性卡里可以有数字，但数字必须带**参照物**和**评价**。

---

## 三、定性卡的四种

### 3.1 国情卡（每国一张，每回合重生成）

```yaml
国: 魏
处境: 君位刚定，国库空空，西河武卒心怀怨望，中山在闹饥荒
体感:
  财政: 存粮告罄，靠借债度日   # 真值: 粮 400 / 年需 1900
  军事: 能守不能攻             # 真值: 三军团两残一不满编
  民心: 魏东秩序初复，中山离心
  士人: 西河学派随吴起出走而凋零
优势:
  - 韩赵仍是盟友，且刚在安邑之会上重新分赃
  - 魏武卒底子在，只是缺一个能服众的统帅
隐患:
  - 中山公以"闯王"为号，正从山中反攻
  - 淮北军团已哗变解体，编制名存实亡
一句话: "魏国现在不是能不能扩张的问题，是能不能不散架的问题。"
```

### 3.2 势力卡（每个 NPC / 派系一张）

```yaml
人: 田文
身份: 国相，三朝元老
诉求: 保住魏国不散架，把相位传给公叔白
底线: 国君绕过他行事 → 会收束君权（历史上真的减了国策条数）
能力: 老成持重，朝中无对手；但不通军事
态度: "你这事做得还行，但不够好"
```

> 这张卡直接决定国策判定：玩家说"我要办西河学宫"，田文会回"西河学派也不是个具体的人，你要找谁呢"。

### 3.3 事件卡（天灾 / 事变 / 倒计时）

```yaml
事件: 中山旱灾
阶段: 已发生 → 军粮无法筹集 → 蝗灾 → 复国军起
征兆: 雨带停在大陆泽，半年滴雨未下
可见性: 朝廷可知（地方上报）
```

**倒计时型**（这类最值钱）：

| 国 | 倒计时 |
|---|---|
| 赵 | 赵侯将死，赵章 vs 赵朝 |
| 秦 | 秦公无嗣，法统不正 |
| 晋 | 祚将终，韩魏觊觎 |
| 中山 | 蓄力中，等乐不书军团离开 |

### 3.4 弹劾卡（判定用的"机制清单"）

玩家的国策能不能落地，取决于**这个国家有没有对应的机制**：

```yaml
魏:
  有: 军法（初立）、屯田（中山军团自筹）、朝议
  无: 学宫、成文法、户籍统计、郡县制
```

> 记录里所有驳回几乎都能归到这张表上：
> "建平陆郡——**要人没人要机制没机制**"、"军功制改革——**缺乏相应机制**，蒋将都掌握不住"。

## 四、数字锚：防止定性漂移

定性层最大的风险是**LLM 编造**。对策：每张卡带 3–5 个**数字锚**，且锚点必须可校验。

```yaml
国情: 魏
锚点:
  - 中山军团年耗粮 700
  - 本次调拨 400（赵150 + 余250）
  - 淮北军团哗变后兵力不足七成
```

规则：

1. 锚点数字由代码注入，LLM **只能引用不能改写**
2. 奏报生成后，代码校验：凡出现的数字必须能在锚点表里找到来源
3. 找不到 → 拒绝该句 / 重写

这正好复用我们已有的"变更单必须可审计"的思路，只是对象换成了**文本**。

## 五、和现有架构的接缝

| 现有设计 | 需要调整 |
|---|---|
| 系数总线（LLM 只输出系数） | **不变**，但输入从"数值表"换成"定性卡" |
| 变更单（Adjust/Transfer/Set） | **不变**，仍是代码唯一写入口 |
| 奏报 | 增强：定性为主，数字作对照 |
| 事件溯源 | 新增：定性卡也要存快照（否则回放时叙事不一致） |
| 势力层 | 从"数值态度值"扩展为"诉求/底线/能力的结构化卡" |

### 新增的流水线步骤

```
① 代码结算 → 真值更新
② 真值 → 定性卡派生（模板 + 关键锚点）
③ 定性卡 + 玩家国策 → LLM 判定（输出系数/驳回理由）
④ 系数 → 代码结算
⑤ 结果 → 奏报（LLM 写，代码校验锚点）
```

②是新增的，也是这次讨论的产物。它的实现可以很朴素：**模板 + 少量 LLM 润色**，不必每回合都调模型。

---

## 六、为什么这样反而更省 token

- 一张国情卡约 300 字 ≈ 200 token；而完整数值表（9 国 × 6 军团 × 人群）轻松上万 token
- 定性卡可以**只生成当前回合相关的部分**（只给正在被问的那一国）
- 奏报生成时也只喂锚点，不喂全表

**结论**：定性层不只是"更好用"，还更便宜。这正好接上崇祯"单局 3000 万 token"的死因。
