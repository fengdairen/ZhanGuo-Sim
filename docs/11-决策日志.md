### D5 ⚠️ 被纠正："20 万营收很少"这句话不成立

用户质疑："20w 营收……很少吗……"

### D8 数据层与显示层彻底解耦，并做出工作台 exe

用户原话：
> "数据层回归更纯粹的数据结构，现在的 Excel 太不方便更改，而且数据和显示层严重耦合，其实不符合游戏制作的理念——我希望我可以通过一个 exe 直接观察和操作数据！"

**决定**：
- Excel 降级为"策划编辑工具"，运行期用 `data/state.json`
- `ZhanGuo.Core` 做成纯 C# 类库，**不引用任何 UI 程序集**
- 用 WPF 做 `dist/ZhanGuo.Workbench.exe`，只管显示与编辑，不做算术
- 公式只存在于 `Economy.cs` 一处

**验证**：写了一个命令行校验器，把 C# 结果与 Excel 缓存值逐项对比——
**284 项、0 偏差**。

**过程中挖出两处隐藏数据**（不挖出来换任何语言都会算错）：
1. **人口权重是逐行的**：魏国邑权重有 30/25/20 三种，不是全局常数。
2. **维护费成本是逐部队的**：常规军 `步×60+甲×150+辅骑×180+车×300`，骑兵 `步×220`，水师 `步×300`——
   而且**越国水师是 250，别国 300**。

这两条直接改变了数据模型：权重和成本都必须变成字段，不能写死。

### D9 所有数据改动改为「变更单」，禁止直接改单元格

用户原话：
> "不要直接改城池数，而是'向某个字段加减多少数值'；比如'将这个品类的人口从魏国转移三个城池到楚国'；其他数据同理。"

**决定**：
- 工作台所有页面改为**只读**
- 唯一写入口是「变更单」：`调整 / 转移 / 设定` 三种操作
- 每条变更必须带**事由**
- 一批变更**原子提交**，一条不合法则整批不落地
- 提交后写 `data/events.jsonl`（前后哈希 + 操作 + 事由 + 结果）

**为什么这是对的**：
"改成 3"和"加 3"语义完全不同。后者可重复、可叠加、可审计；
前者一旦重放就会出错——**这正是崇祯「重复抄家」和「读档误清算」的根源**。

**额外收益**：人和 LLM 从此共用同一种输入格式。
M3 接模型时不需要另造协议，模型输出的就是 `ChangeOp` 的 JSON。

**验证**：写了 20 项行为测试，覆盖加减、跨地转移、新建目标人群、
超额/负值/空事由/连续量拒绝、整批原子性、预览不改状态。全部通过。

### D10 时间线锁定 **BC 390**（两次校准错误的纠正）

**第一次错误**：我在做人口考证时，拿战国晚期的材料（苏秦"临淄七万户"，约前 300 年）去校准，还把**咸阳**改成了"都"、人口 22.5 万。

用户纠正：

**第二次错误**：我据此把时间线记成 **BC 400**，并写进了所有文档。这是错的。

**最终确认（2026-11-11，依据推演记录）**：
- 记录里明确写着「**剧本开始时（bc390）**」「**BC389 开春**」第一回合
- 用户确认：**时间线 = BC 390**

**BC 390 的实际格局**：
| 国 | 都城 | 备注 |
|---|---|---|
| 秦 | **雍** | 咸阳前 350 才建，此时只是个小邑 |
| 魏 | **安邑** | 前 361 才迁大梁 |
| 赵 | **中牟** | 前 386 方迁邯郸 |
| 韩 | **阳翟** | 前 375 灭郑方迁新郑 |
| 越 | **琅琊** | 不在会稽 |
| 齐/楚/燕/宋/鲁 | 临淄/郢/蓟/睢阳/曲阜 | 不变 |

**图上的"都"实际更像"大城"**，与 BC390 的都城名单并不一致——这是待定项。

**处理**：咸阳回滚为 `邑 / 1.2 万`；全部文档 BC400 → BC390；建立规则——**动数据前先问，不擅自改**。

**教训**：
1. 史料是有时间坐标的。"临淄七万户"不能用来校准比它早一百年的世界。
2. **不确定的年代不要自己推**。我从只言片语推出"BC400"，错了整整十年，还扩散进了六份文档。

### D12 地图层的工具化路线

用户的诉求一路演进，最后收敛为一套"协作编辑"工具：

1. 一开始是"一题一屏的勘误台"（自动定位镜头 + 回车确认）
2. 后来要**分组**（11 组，便于分工）→ 做了 11 个 HTML
3. 再后来**取消分组**，改单页 + 记录"改了哪些"（`changed` 列）
4. 最后要求**整合改名 / 改人口 / 移动标点 / 新增 / 删除** → 完整地图编辑器
5. 以及"不下载也能保存" → 用 File System Access API **绑定本地文件自动写盘**

**设计要点**：
- 顶部大字显示当前名字，比对更直接
- 导出带 `oname / opop / ox / oy` 原始值，合并时只应用真正改动的条目
- 颜色区分：改过的名字/坐标在界面上有标记

### D13 引入人口表：从"一城一个数字"到"城市 × 人群 × 数量"

用户要求：

> "人口应当有新的表格，比如一个城可能有多种人口……人口应有一系列反映他们文化、认知和政治倾向的字段（其实一个简介字段也就够了）。先把所有城邑的人口都设为基础人群『无认同人口』，他们并无确切的民族或国家认同，只是认为自己是种地的野人。"

**决定**：

- 人口拆成两张表：
  - `groups.csv`（人群库）：`name` + `note`（简介＝文化/认知/政治倾向）
  - `populations.csv`（人口条目）：`city_id` + `group` + `amount`
- **城池总人口改为派生值**（= 该城所有条目之和），不再单独存字段
- 初始迁移：1094 条记录，全部为「无认同人口」，合计 2266.2 万
- 工具分工（用户明确要求）：
  - **人群库编辑器**只管"世界上有哪些人群"，不出现地图
  - **地图编辑器**决定"哪个城有几万什么人群"，只能从人群库选，不能新建

**为什么拆**：一边是世界观设定（楚人是什么人），一边是空间分布（哪里住着多少楚人）。
两者修改频率与操作场景完全不同。

**为什么总数要派生**：两处各存一个总数，迟早不一致——崇祯那套表就是"人口表加起来 ≠ 总人口"而无人发现。
