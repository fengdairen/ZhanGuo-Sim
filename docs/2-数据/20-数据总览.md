## 3. 单位约定（最容易出错的地方）

| 量 | 单位 | 备注 |
|---|---|---|
| `nodes.csv` 的 `pop` | **万** | 如 `22.5` = 22.5 万人 |
| `state.json` 的人口 | **千人** | 如 `1170` = 117 万人 |
| `populations.csv` 的 `amount` | **万** | 与 nodes 一致 |
| 产值 | 经济表单位 | 公式里用**千人**，所以 `pop × 10` |

> ⚠️ **万 vs 千** 相差 10 倍。经济下放到城池时就踩过这个坑（产值只有 1/10）。

---

## 4. 三条数据规则

1. **一个量只有一个真相**。城池总人口 = 该城所有人口条目之和（派生），不单独存。
2. **派生值不落盘**。产值、总人口、汇总都在读的时候算，避免不一致。
3. **作者改数据走工具，不走手改**。手改 CSV 会绕过校验（例如归属国 id 打错）。

## 5. 数据从哪来

| 数据 | 来源 |
|---|---|
| `state.json` | `备份.xlsm` 导出（`tools/pipeline/export_state.py`） |

| `ownership.csv` | 初始化为空，靠人工分配 |
| `economy.csv` | 按城池类型给初始值（都 0.75/12/0.75 等） |

## 6. 下一步的数据缺口

| 缺口 | 影响 |
|---|---|
| 城池没有**产业类型**（农/工/商/渔盐/矿冶） | 税种 × 税基挂不上去 |
| 城池没有**资源**标记（铜/铁/盐/玉…） | "有资源≠有收入"这条规则无法执行 |
| 部族没有**范围多边形** | 判断不了"某城是否在某部族内" |
| 没有**历史归属** | 做不了"某年易主" |
| `group_anchor.csv` 未填 | 2310 万真实人口仍落不到具体城 |
