# 10 · 项目定义：五层架构与 LLM 的职责边界

> 状态：**项目定义草案**（等待拍板 §9）
> 一句话：**一个"文字国策 → 五层结构化变更 → 可审计事件流"的战国模拟器。LLM 只做翻译与判断，结算全部由确定性代码完成。**

---

## 0. 先把五层分个类

五层不是平级的。分成三类，很多设计问题会立刻变简单：

| 类别 | 层 | 特征 | 能不能让 LLM 直接写 |
|---|---|---|---|
| **模拟器** | 经济表、军事层 | 有内在动力学，必须守恒（钱不能凭空生、兵不能凭空来） | ❌ 绝对不能 |
| **修改器** | 政策树、势力层 | 本身不产生数值，只产出**系数**和**离散状态** | ✅ 这是它的主场 |
| **容器** | 地图区 | 拓扑与归属，变化来自其他层的结论 | ⚠️ 只读，写入由结算决定 |

`[判读]` 这个分类是整个架构的地基：
**LLM 只碰"修改器"，不碰"模拟器"。**
崇祯的错就是把 LLM 直接接在了"模拟器"上。

## 1. 逐层定义

### 1.1 经济表（模拟器）

| 项 | 内容 |
|---|---|
| **状态** | 人口（都/城/邑/野地）、税目/税基/税额/效率、工程/军事/行政开支、国库、判定修正 |
| **规则** | 全部写在公式里：`上税=税额×效率`、`总税收=Σ上税×√(1−腐化)`、`军事开支=Σ维护费÷√(1+军治清明)`、`行政开支=(都×12+城×10+邑×6+人口×0.8)÷行政建设^0.6` |
| **上游** | 地图（都邑数量与归属）、政策树（税种解锁、制度系数）、势力层（腐化/行政建设/执行折扣）、军事层（部队规模→维护费） |
| **下游** | 可支配财政、补给上限、能否支撑某次军事行动 |
| **LLM 权限** | 只能填**输入**：税额、效率、工程立项、判定修正（须带事由） |

**铁律：公式不归 LLM 管。** 它只能调旋钮，不能改传动比。

### 1.2 地图区（容器）

| 项 | 内容 `[待你提供]` |
|---|---|
| **状态** | 邑/城/都 的归属、相邻关系、道路、关隘、地形 |
| **规则** | 行军路径、补给线长度、战场地形选取、税基的地理归属 |
| **上游** | 军事层（占领）、外交（割让）、政策（筑城/道路） |
| **下游** | 经济表（税基分组）、军事层（行军与战场） |
| **LLM 权限** | **只读**。领土变化必须由"战斗结果"或"条约"这类确定性事件触发 |

`[判读]` 地图是唯一"纯被写"的层。它的写入者应该是**结算器**，不是模型。

### 1.3 军事层（模拟器）

你已有一个战场模拟器，这里只定义**接口边界**。

| 项 | 内容 |
|---|---|
| **状态** | 部队：步卒/甲士/辅助骑兵/战车数量、训练度、战备等级、补给等级、驻地、统帅、士气 |
| **规则** | 维护费公式（经济侧）+ 战场模拟（你已有） |
| **接口（建议纯函数）** | `BattleResult Resolve(BattleInput input)` |
| **BattleInput** | 双方编成、训练、士气、补给、将领能力、地形、战术选择、天气 |
| **BattleOutput** | 胜负、双方伤亡、溃散、缴获、士气变化、占领结果、耗时 |
| **上游** | 经济表（能否供养）、地图（位置/地形）、政策树（军制/编成上限/训练模式）、势力层（军令贯彻度） |
| **下游** | 地图（归属）、经济表（损耗/维护费）、势力层（威望/恐慌） |
| **LLM 权限** | **不参与战斗结算**。只决定：是否开战、谁挂帅、打不打、撤退不撤退、补给给不给够 |

`[判读]` 战场模拟器是纯函数的话，整场战斗可回放、可复盘、可做"如果当初多给两千人"的对比——这本身就是产品卖点。

### 1.4 政策树（修改器）

| 项 | 内容 |
|---|---|
| **状态** | 17 项制度 × I–IV 级 + 每级的文案 + 前置条件 + 改革成本 |
| **规则** | 升级需要：前置等级、改革点、财政投入、政治阻力 |
| **上游** | 玩家诏书（要改哪项）、势力层（支持/反对）、经济表（付不付得起） |
| **下游** | 产出系数：腐化上限、征收效率、军治清明、行政建设上限、编成上限、兵种解锁 |
| **LLM 权限** | 判断"这道国策是不是在推某项改革"，以及"推进了几成" |

**关键**：政策树是**离散状态机 + 成本**，天然适合代码裁定。LLM 只负责把"整军经武"这种模糊措辞映射到"军事训练模式 → 目标 II 级"。

`[判读]` 这里有个很妙的设计机会：**改革不是一次点击，而是一个有进度条的过程**。
"废井田"不是一道诏书就成，而是 5–10 个回合、每回合投入、每回合遭遇阻力。这正好对应先秦变法的真实节奏（商鞅变法用了近二十年）。

### 1.5 势力层（修改器，LLM 主场）

| 项 | 内容 |
|---|---|
| **状态** | 每个 NPC：姓名、官职、所属派系、**利益诉求**、权势、对国君的态度、执行力 |
| **状态** | 每个派系：势力值、核心诉求、可容忍底线、与其他派系关系 |
| **规则** | 态度→执行折扣；权势→改革阻力；诉求被触犯→反制 |
| **上游** | 玩家诏书（动了谁的利益）、其他层的结算结果（谁受赏谁受罚） |
| **下游** | **执行折扣**（进一切结算）、改革阻力、政变/叛逃风险、奏报口径 |
| **LLM 权限** | 全部。判断立场、是否阳奉阴违、奏报是否说谎 |

`[判读]` 势力层是整个系统里唯一"必须靠模型"的地方，因为它处理的是**意图、利益与欺骗**——这三样没法写成公式。

## 2. 核心设计：系数总线（Modifier Bus）

这是我认为整个架构最关键的一个决定，也是把"软判断"变成"硬参数"的转换器。

### 2.1 问题

"这道诏书激怒了士绅，所以赈灾粮只到了三成"——这句话怎么进代码？

如果让 LLM 直接写"到达率 = 0.3"，那就回到了崇祯：**不可复现、不可解释、不可学**。
如果完全用公式，又表达不出"谁在阳奉阴违"。

### 2.2 解法：所有软判断只产出系数

```
LLM 输出：{ faction: "鲁国士人", attitude_delta: -15 }
                ↓  规则表（确定性）
系数总线：execution_discount: 1.0 → 0.72
                ↓
结算器：到达率 = 制度系数 × 执行折扣 × 护送系数 × 距离衰减
```

**LLM 永远不输出结果，只输出"对系数的驱动"。** 系数怎么算结果，由代码决定。

### 2.3 系数清单（初始版）

| 系数 | 来源 | 消费方 | 取值 |
|---|---|---|---|
| 腐化 | 势力层 + 政策树 | 总税收 | 0–1 |
| 行政建设 | 政策树 + 经济投入 | 行政开支 | 0.3–1.2 |
| 军治清明 | 政策树 + 军队统帅 | 军事开支 | 0–1 |
| **征收效率** | 政策树 + 地方势力 | 税基→实收 | 0.2–1.0 |
| **执行折扣** | 势力层 | 一切诏书执行 | 0.1–1.0 |
| **军令贯彻** | 势力层 + 统帅 | 战场先手/阵型 | 0.3–1.0 |
| **地方配合** | 地方势力 | 工程/赈灾/征发 | 0.1–1.0 |
| **改革阻力** | 势力层 | 政策树升级成本 | 0.5–3.0 |

`[判读]` 这套总线的价值在于：**玩家可以学会它**。
"我知道士绅反对，所以先给他们一点好处再赈灾，执行折扣就上去了"——这是策略游戏的本质乐趣。
崇祯给不了这个，因为它每次都是随机给个数。

## 3. 一条国策的五层投影

以"赈灾"为例，展示"一条国策 → 多层变更"：

```
玩家诏书：「着户部拨银三十万两、粮二十万石，赈济陕西，遣御史监之，沿途敢有克扣者斩。」
```

| 层 | 变更 | 确定性 |
|---|---|---|
| **意图解析** | 动作=赈灾；对象=陕西；银 30 万；粮 20 万；监查官=某御史 | LLM |
| **经济表** | 国库 −30 万；粮仓 −20 万；若不足→封驳 | 代码 |
| **地图** | 粮道 A→B，途经 C 邑；距离 6 日 | 代码 |
| **军事** | 玩家未派护送 → 无护送；被劫概率基线 | 代码 |
| **政策树** | 赈灾相关制度等级：II（地方治理）= 系数 0.55 | 代码 |
| **势力** | 陕西地方势力态度 −10（越过他们直接派御史）→ 执行折扣 0.72；士绅配合 0.5 | LLM 判态度 → 代码转系数 |
| **结算** | 到达率 = 0.55 × 0.72 × 1.0 × 0.85 ≈ **0.34** | 代码 |
| **回执** | "臣奉旨赈陕，然御史未至而仓已空其三…" | LLM |

`[判读]` 注意：**玩家能看到 0.34 这个数，也能看到它是哪几个系数乘出来的。**
这就是"可解释性"——崇祯给不了，我们天生就有。

## 4. 一回合的结算时序

顺序不能乱。这是六个"必须先于"的约束：

```
① 收集国策（所有玩家）
② 意图解析 → 变更单（LLM，只产提议）
③ 【读】势力层：上回合态度 → 本回合执行折扣
④ 【写】政策树：改革推进判定（前置/成本/阻力）
⑤ 【写】经济表：收入 → 各项开支 → 国库
⑥ 【写】军事层：编练/行军/战斗（调战场模拟器，纯函数）
⑦ 【写】地图：领土/占领/道路变化
⑧ 【写】势力层：依据本回合结果，更新态度/权势
⑨ 【写】延迟效果队列：到期结算（欠饷、工程完工、灾害恶化）
⑩ 生成回执（LLM，只读结算结果）
⑪ 提交：事件日志 + 状态快照 + 内容哈希
```

**为什么是这个顺序：**

| 约束 | 理由 |
|---|---|
| ③ 在 ⑤ 之前 | 用**上回合**的态度决定本回合执行——不能"这回合得罪了他，这回合马上报复" |
| ④ 在 ⑤ 之前 | 改革先定系数，再算收支 |
| ⑤ 在 ⑥ 之前 | 先看付不付得起军费，再决定能不能出兵 |
| ⑥ 在 ⑦ 之前 | 打完才改地图 |
| ⑧ 在 ⑥⑦ 之后 | 态度变化是对**结果**的反应 |
| ⑨ 最后 | 延迟效果只在本回合既成事实之后才到期 |

`[判读]` 崇祯的"下狱后不认诏令""军队解散了还在扣维护费"，本质都是**没有固定时序**。

## 5. 国策 → 变更单（IR）

```jsonc
{
  "edict_id": "uuid",           // 幂等键
  "turn": 12,
  "nation": "lu",
  "raw_text": "……",             // 原文永久保留
  "intents": [
    {
      "kind": "RELIEF",
      "target": { "region": "shaanxi" },
      "params": { "silver": 300000, "grain": 200000, "supervisor": "person:yushi_x" },
      "confidence": 0.91,
      "evidence": "拨银三十万两、粮二十万石",
      "assumptions": ["未指定护送部队"]
    }
  ],
  "unparsed": ["敢有克扣者斩"],   // 未识别部分，显式暴露
  "layer_projection": {          // 由代码补全，不由模型填
    "economy": [...], "map": [...], "military": [...],
    "policy": [...], "faction": [...]
  }
}
```

**三条规矩：**
1. `assumptions` 必须显式——模型自己补的要让玩家看见。
2. `unparsed` 不许静默丢弃。
3. `layer_projection` **由代码生成**，模型只填 `intents`。

## 6. 技术栈与 Excel 的定位

### 6.1 一个必须先定的问题

**Excel 是"运行期状态"还是"编辑期工具"？**

`[建议]` **编辑期工具。** 运行期不要读写 xlsm。

理由（都来自 08 号文档的实测）：
- 没有回合字段、没有事件日志 → 无法回放
- 税基是硬编码区间 → 插入行必错位
- 公式与数据混在一起 → 无法做不变量校验
- 读档可能触发副作用（崇祯的原罪）

### 6.2 建议的数据流

```
策划编辑：Excel（保留你熟悉的手感）
              ↓ 一次性导出
运行期   ：JSON / SQLite（权威状态）
              ↓ C# 对象
结算引擎 ：纯函数 Resolve(state, edict) -> (state', events)
              ↓ 事件 JSONL
回放/审计：任意回合重放、分支、导出回 Excel 给人看
```

**导出器**是唯一需要写一次的东西，之后 Excel 只用于"人读人改"。

### 6.3 C# 侧骨架（示意）

```csharp
public interface ILayer {
    string Id { get; }
    void Apply(GameState state, ChangeSet change, TurnContext ctx);
    IReadOnlyList<Violation> Validate(GameState state, ChangeSet change);
}

// 结算引擎：纯函数，无副作用
public static class TurnResolver {
    public static (GameState next, IReadOnlyList<GameEvent> events)
        Resolve(GameState state, IReadOnlyList<Edict> edicts, IRandom rng);
}

// 战场模拟器的契约
public interface IBattleSimulator {
    BattleResult Resolve(BattleInput input);   // 纯函数、可回放
}
```

`[判读]` 你已有 Unity/Godot/UE 任一引擎的经验，前端用哪个都不影响核心。
**核心引擎应该是纯 C# 类库**，不依赖引擎——这样能在命令行跑回归测试，也能被任何引擎引用。

## 7. 与崇祯的对照

| 维度 | 崇祯 | 本项目 |
|---|---|---|
| 判定 | LLM 自由裁量 | 公式 + 系数总线 |
| 数值写谁 | LLM 函数调用直写 | 结算器 |
| 可解释性 | 无（玩家不知道为什么是三成） | 有（到达率是四个系数的乘积） |
| 可学习性 | 无（每次随机） | 有（规则稳定，可优化） |
| 成本 | 3000 万 token/局 | 估计 <100 万/局 |
| 失败模式 | 假数据、漂移 | 系数调错（可测试） |

## 8. 这个项目真正的差异化

不是"AI 会写诏书"，也不是"AI 会推演"。

> **是"AI 会推演，但推演的规则是你能学会的"。**

崇祯的所有差评，本质都是"我不知道为什么"。策略游戏玩家可以接受**难**，不能接受**不可知**。

## 9. 已拍板（2026-11-10）

| 决策 | 结论 | 影响 |
|---|---|---|
| 形态 | **单机游戏**（gameplay UI 后做） | 无服务端/账号/并发；存档在本地；LLM 接入方式需单独定（§11.2） |
| 回合 | **一季（三月）** | 一局 40–80 回合；变法节奏按季度计（§11.4） |
| 玩家 | **只当国君**，无真人推演者 | 势力层是"环境"不是"可扮演角色"；世界必须能自转（§11.1） |

### 9.1 仍然未定

1. **LLM 谁付费**：玩家自填 Key（免费、门槛高）／ 你代理（可控、你要扛成本）／ 混合（本地小模型兜底 + 云端增强）。
2. **地图粒度**：邑（数十个）／ 城（百余个）。
3. **战场模拟器的输入输出形状**（需要你给接口）。
4. **政策树节点数与层级**（决定一局时长）。
5. **胜利条件**：统一？存续？还是"分数制"（像 CK 那样没有硬终点）。

## 10. 单机形态带来的四个新约束

### 10.1 世界必须自己会动

没有真人推演者了——**你下完诏书，如果世界不动，游戏就死了**。

需要一个**事件发生器**（CK3 式）：

```
每回合至少触发 N 件事，从事件池里按 条件 ∧ 权重 ∧ 互斥 抽取
事件池 = 天灾 / 邻国动作 / 士绅请托 / 将领请战 / 宗室争位 / 变法反弹 / 商路变化
```

三条硬要求：
1. **条件驱动**，不是纯随机——"粮食欠收"要在有旱情的地方发生。
2. **互斥**——不能同一回合既"大丰收"又"大饥荒"。
3. **可归因**——事件文案要指向真实状态（哪个邑、哪个人、哪个制度等级）。

`[判读]` 这一层不需要 LLM 生成。用模板 + 槽位填充（`{邑名}大旱，{官员}请开仓`）就够了，快且便宜。
只有在玩家追问时，才让 LLM 展开叙事。

### 10.2 LLM 接入的三种方案

| 方案 | 成本 | 门槛 | 风险 |
|---|---|---|---|
| **A. BYOK**（玩家自填 Key） | 零 | 高，筛掉大部分玩家 | 无 |
| **B. 你代理** | 你扛 | 低 | **崇祯的老路**：重度玩家烧穿预算 |
| **C. 本地小模型 + 云端增强** | 低 | 中 | 工程量大，效果不稳 |

`[建议]` **A 为主 + B 的小额度赠送**：
- 内置一小笔免费额度（够玩 3–5 局），让玩家先尝到甜头；
- 之后提示"接入你自己的 Key"，并显示"这道诏书解析消耗 ≈ 0.02 元"。

**为什么我们敢这么做**：我们的单局 token 消耗估计 <100 万，是崇祯的 1/30。
而且**结算不烧 token**——玩家就算不接 Key，用规则化输入也能玩。

`[判读]` 这一点很重要：**我们的系统可以在"没有 LLM"的情况下退化运行**（玩家从动作菜单里选）。
崇祯做不到，因为它的判定本身就是 LLM。这是我们相对它最大的工程优势。

### 10.3 存档、回放与分支

单机 = 存档就是产品的一部分。

```
存档 = 初始状态快照 + 事件日志（JSONL）+ 随机种子
```

- **回放**：从快照重放到任意回合，纯函数，无副作用。
- **分支**：从第 30 回合分叉，做"如果当初不杀他"的对比。
- **体积**：只存 diff，不存全量状态，一个 60 回合的存档应该 < 2 MB。

`[判读]` 分支回放是**单机策略游戏最好的宣传素材**，也是我们相对崇祯的"可解释性"卖点的自然延伸。

### 10.4 一季制下的变法节奏

一季 = 三个月。一局按 **60 回合（15 年）** 设计。

**改革点产出：**

```
每回合改革点 = 2 + 行政建设 × 3 + 威望修正     （约 3–6 点/季）
一局总产出 ≈ 200–350 点
```

**升级成本（累计）：**

| 升级 | 累计成本 | 现实时间 |
|---|---:|---|
| I → II | 6 点 | 约 1 年 |
| II → III | 15 点 | 约 2 年 |
| III → IV | 30 点 | 约 3 年 |

**同时推进多线时效率衰减：**

```
若同时推进 N 项，每项获得 1 / (1 + 0.5×(N−1)) 的效率
```

`[判读]` 算一笔账：一局 200–350 点，全升满 17 项到 IV 需要 17×51 ≈ 867 点。
**所以一局最多只能把 4–6 项推到头。**

这就是策略轴：**专精军事？专精财政？还是铺开到 II 级求均衡？**
`[判读]` 这也天然解释了先秦变法的历史感——**没有哪个国家能同时把一切改完。**

## 11. 建议的推进顺序

| 阶段 | 产出 | 验证什么 |
|---|---|---|
| **M0** | Excel → JSON 导出器 + C# 状态模型 | 数据能跑通、公式可复现 |
| **M1** | 结算引擎（**无 LLM**）：脚本化国策 → 经济/军事结算 | 数值守恒、可回放 |
| **M2** | 事件发生器 + 势力层（仍无 LLM） | 世界能自转 |
| **M3** | 接 LLM：只做 `intents` 解析 | 解析准确率 > 90% |
| **M4** | 系数总线 + 政策树 | 执行折扣自洽 |
| **M5** | 接战场模拟器 | 军事层闭环 |
| **M6** | 回执生成 + gameplay UI | 可玩性 |

`[判读]` **M0–M2 全程不接 LLM。** 这条纪律比任何架构都重要：
先用假国策和假事件把整条流水线跑通，否则你永远无法区分"是模型错了还是我的结算错了"。
崇祯的所有 bug 都出在"两种错误混在一起"。

`[判读]` 另外，M0–M2 的产物是一个**能在命令行跑的纯 C# 类库**，不依赖引擎。
这样你换 Unity / Godot / UE 都不影响核心，也能写自动化回归测试。
