# 52 · 同类方案与工程范式

> 目的：不要重新发明轮子。文字治国、LLM 当世界引擎这两件事，都已有可借鉴的成熟做法。
> 结论先行：**学界已经给出了正确的架构——"模型提议、代码裁决、状态可回放"，我们直接用。**

---

## 1. 同类商业游戏：它们怎么处理"文字 → 系统"

### 1.1 Suzerain（《总统先生》）

- 纯文字政治模拟，玩家通过**对话选项 + 法案/行政令**推进。
- 关键设计：**双轴意识形态**（民主/威权 × 资本主义/计划经济）+ **延迟后果**。很多决定在数十回合后才反噬。
- 参考价值：**"延迟后果"的商业验证**。它的代价是分支全靠人工写——这正是 LLM 想替代的部分。
- 可借鉴：**决策要记账**。Suzerain 会记住你三章前的一句承诺。

### 1.2 Crusader Kings III

- 角色 + 派系 + 事件 + 阴谋，状态极其结构化（角色、头衔、好感度、契约）。
- 关键设计：**状态是权威的，事件是状态的前置条件驱动的**。事件不是随机的，是"检查条件 → 触发"。
- 可借鉴：
  - **事件表 = 条件 + 权重 + 互斥**（可直接作为"触发式事件"的参考实现）。
  - **可执行动作有前置条件**（下狱的前提是对方在你的领地内）。这直接对应崇祯的"下狱后不认诏令"bug。

### 1.3 King of Dragon Pass / Six Ages

- 部落治理，事件以"场景 + 选择 + 神明/ council 意见"呈现。
- 可借鉴：**议事会成员有立场，且立场可被玩家的话影响**——这与崇祯的廷议系统几乎一致。
- 提醒：它的成功靠**手写事件库的密度**，不是靠生成。

### 1.4 Reigns

- 极简：左右滑动，四个资源条（教会/民心/军队/财政）。
- 可借鉴：**资源条就是"存量的可视化"**。简单、可读、玩家能立刻理解代价。
- 提醒：它证明"少而清晰的指标"比"数千维度"更好玩。

### 1.5 Democracy 4

- 政策 → 模型化影响（数百个模拟量），有明确的因果链和延迟。
- 可借鉴：**政策不是直接改数值，而是改"参数"，参数再驱动模拟**。这是"税率 → 收入"的正确做法。

### 1.6 AI 原生游戏的失败教训：AI Dungeon

- 纯文本生成，无持久状态。结果是：**世界会漂移、NPC 会失忆、设定会被遗忘**。
- 这是"让模型当世界"的反面教材，也是崇祯 3000 万 token 路线的前车之鉴。
- 结论：**生成负责表达，状态必须外置。**

## 2. 学术方案：Orchestrated Reality（最贴合此问题的一篇）

> Huang, Li, Fang. *Orchestrated Reality: From Role-Play to Living, Playable Game Worlds — LLM-Driven World Simulation as a Parameterized-Action POMDP.* 2026.
> 这篇论文基本把我们想做的事形式化了，强烈建议作为架构蓝本。

### 2.1 它对现有系统的诊断（三条，每条都命中崇祯）

1. **无状态（Statelessness）**：会话结束世界就没了，"记忆"只是上下文邻近性。
2. **未校验写入（Unvalidated writes）**：模型可以断言任何世界变化，状态静默漂移并累积矛盾。
3. **单体代理（Monolithic agency）**：一个 prompt 同时负责叙述环境、扮演所有角色、裁决规则——把本该分离的职责混在一起。

### 2.2 它的核心方案：PDVA 管线

**世界是一棵 JSON 实体树**（不是一段文本），每回合通过四步推进：

| 步骤 | 做什么 |
|---|---|
| **P**lan | 从规范状态中切出与本次动作相关的**有界上下文** |
| **D**iff | 模型返回 `(narrative, Δ)`：叙事文本 + 结构化变更提议 Δ |
| **V**alidate | 每个变更 δ 必须同时满足 `SchemaOK ∧ PermOK ∧ RuleOK` |
| **A**pply | 通过校验的变更**原子提交**，并对新状态做 **SHA-256 内容哈希** |

形式化：

```
Valid(δ) = SchemaOK(δ) ∧ PermOK(δ, actor) ∧ RuleOK(δ, rules)
s_{t+1}  = Apply(s_t, {δ | Valid(δ)}),  h(s_{t+1}) = SHA256(serialize(s_{t+1}))
```

### 2.3 三个我们认为必须照搬的机制

1. **动作参数化**：`a = (k, x_k)` — 离散意图类型 `k` + 结构化参数 `x_k`。
   → 对应诏书解析里的"意图类型 + 参数"两段式。
2. **记忆是注入的，不是回忆的（Memory is injected, not recalled）**。
   每回合组装一个 **context pack**（固定种子集 + 相关度排序的有界记录），直接注入 prompt。
   → 状态相关的 prompt 是**提交状态的确定性函数**，而不是聊天窗口的残留。
3. **事件溯源 + 内容哈希**。
   每回合记录 `e_t = (t, actor, kind, h(s_t), h(s_{t+1}), Δ_applied)`。
   → 可审计、可调试、可从任意点分支。

### 2.4 权限模型：deny-first, 每回合单一写入者

- 每个代理有契约 `c = (id, type, R, W)`，读/写 glob，**默认拒绝**。
- **每回合只有一个 world-agent 拥有写权限**，所有提议收敛为一次原子提交 → 无竞态。
- 提交是 **hash-first**：先算内容哈希，再落盘；任一写入失败则整体不落地。

`[判读]` 这条同时能解释崇祯的两类 bug：无单一写入者 → "重复抄家"；无原子提交 → "读档误清算"。

### 2.5 值得注意的诚实之处

论文承认：**拒绝也是体验的一部分**——"narrated validation rejections increase felt consequence"（把校验失败讲成故事，反而增强玩家的"后果感"）。

`[判读]` 理想形态下，"诏书被驳回"不应是错误弹窗，而应是一封**驳斥的奏疏**——明代有"封驳"制度，题材天然自洽。

## 3. 工程范式：让 LLM 安全地驱动游戏动作

来自游戏工程实践（Playgama 等）的硬规则，几乎可以当作判定层的验收清单：

| # | 规则 | 对判定层的含义 |
|---|---|---|
| 1 | **绝不让模型的原文本当代码执行** | 只接受结构化输出 |
| 2 | 用**封闭动作清单 + 类型化参数** | 诏书动作枚举（赈灾/调兵/加税/任免…） |
| 3 | 用 function calling / schema，而不是解析自由文本 | 强制 JSON Schema |
| 4 | 校验**取值范围与实体存在性**（不只是 schema） | 目标 id 必须在状态中真实存在 |
| 5 | **速率限制 + 全量记录**被接受的动作 | 事件日志 |
| 6 | 原型阶段先用**对抗性 prompt** 打一遍（骗装备、跳任务） | "绕过财政""直接杀大臣"类诏书 |

补充的经典工程手段：

- **幂等键**：每条诏书一个 `edict_id`，重复提交不重复结算。
- **纯函数结算**：`resolve(state, edict) -> (state', events)`，无隐藏副作用。
- **快照 + 增量**：每 N 回合存快照，其余存增量，支持回放与时间旅行。
- **双向账本**：每条分录带方向（借方/贷方）与科目，禁止模型填正数。
- **前置条件表**：每个动作声明 `requires`，不满足则走"封驳"流程。

## 4. 反模式清单（我们绝对不做的事）

| 反模式 | 为什么危险 | 崇祯的对应事故 |
|---|---|---|
| 让模型直接写数值字段 | 方向错、量级错、无审计 | 支出误记收入 |
| 用聊天历史当状态 | 长局必漂移，成本爆炸 | 3000 万 token 仍失忆 |
| 一条 prompt 干所有事 | 职责混淆，无法定位错误 | 私聊答非所问 |
| 结算不是纯函数 | 读档/重放产生副作用 | 读档误清算库银 |
| 无幂等 | 重复执行 | 重复抄家 |
| 无实体绑定 | 指代错误 | 抄错人 |
| 单轮允许大幅变更 | 模型"消化不良" | 一次建太多省份建筑推演不认 |
| 跨期计算交给模型 | 无法保持一致性 | 摊销被当成一次性扣款 |

---

## 5. 结论

> 商业游戏证明了**"延迟后果 + 资源挤压"是好玩的**；
> 学术界证明了**"JSON 状态 + PDVA + 事件溯源"是可行的**；
> 崇祯证明了**"跳过后者直接上模型"会在长局里崩**。
>
> 换句话说：崇祯有了 PDVA 里的 **P 和 D**，但 **V 很薄、A 几乎不存在**。
> 这不是模型能力的差距，是**状态管理范式的差距**。
