# 07 · 术语表

> 这份文档只做一件事：把我在调研里用到的缩写和行话，用大白话解释清楚。
> 优先读这里，再看 01–05，会顺很多。

---

## PDVA

**Plan → Diff → Validate → Apply**，四步流水线。

解决的问题：**大模型想改世界状态时，怎么保证它改得对、改得动、改坏了能查。**

一句话：**模型负责提议，代码负责裁决。**

| 步骤 | 干什么 | 输出 |
|---|---|---|
| **Plan** | 从庞大状态里，只挑出跟本次命令**相关的一小块**塞进模型上下文 | 一段有界的上下文 |
| **Diff** | 模型返回两样东西：**给人看的叙述** + **给机器执行的改动清单** | `(叙事文本, 改动列表)` |
| **Validate** | 代码逐条审：字段名/类型对不对、这个人有没有权改、规则允不允许 | 通过 / 驳回 |
| **Apply** | 通过的改动**原子提交**，算内容哈希，写进事件日志 | 新状态 + 一条可回放的事件 |

三道校验关：
- `SchemaOK` — 字段名存在、类型正确
- `PermOK` — 提议者对该字段有写权限
- `RuleOK` — 不违反游戏规则（钱够不够、人还在不在、槽位空不空）

**为什么需要它**：大模型会"断言状态"——叙述里写"国库已拨银三十万两"，但没核实过国库有没有钱。跑几回合，状态就静默漂移、自相矛盾。PDVA 把"改不改"的权力收回给代码。

**体检表用法**：任何"LLM 改状态"的系统，拿这四行对照，缺哪行就出哪一类 bug。

- 缺 **P** → 上下文爆炸、成本失控（崇祯：3000 万 token/局）
- 缺 **V** → 数值乱写、方向记错（崇祯：支出误记收入）
- 缺 **A** → 重复执行、无法回放（崇祯：重复抄家、读档误清算）

出处：Huang, Li, Fang, *Orchestrated Reality*, 2026（见 06-参考资料）。

## 参数化动作（Parameterized Action）

把玩家的自由文本，压成 `a = (k, x)`：
- `k` = 离散的意图类型（赈灾 / 调兵 / 加税…）
- `x` = 这个类型专属的结构化参数

好处：动作空间封闭，可以校验、可以打日志、可以回放。
对应诏书解析："诏书 → 意图类型 + 参数"。

---

## PA-POMDP

**Parameterized-Action Partially Observable Markov Decision Process**（参数化动作的部分可观测马尔可夫决策过程）。

拆开看：
- **POMDP**：玩家看不到完整状态，只能看到"呈现出来的观察"（在崇祯里就是**奏报**，而奏报可能失真）。
- **参数化动作**：见上一条。

论文用这个框架是为了**数学上严谨**，说明"LLM 当转移函数"这件事是可以形式化的。

`[判读]` 对我们的实际工作：**不用懂这个缩写也能用 PDVA**。它的价值在于两句话——
1. 玩家看到的是"投影"，不是真相（→ 奏报可以骗人，这是玩法）。
2. 只要转移函数是纯函数，世界就是马尔可夫的（→ 可回放）。

## 事件溯源（Event Sourcing）

不存"当前状态"，存"发生过哪些事"，当前状态由事件**重放**得到。

```
初始状态 + [事件1, 事件2, 事件3, ...] → 当前状态
```

好处：可审计、可回放、可时间旅行、可从任意点分支。
代价：状态大了要配快照（每 N 回合存一次全量）。

崇祯的反面案例：**读档时误触发了一次结算**——说明它的存档不是"事件重放"，读取本身带了副作用。

---

## 内容哈希（Content Hash）

把状态序列化后算一个 `SHA-256` 指纹。

用途：
- 判断"状态真的变了吗"（没变就不必写盘）
- 事件里记录 `before_hash / after_hash`，可验证链条没被篡改
- 存档去重、分支比对

---

## 幂等（Idempotent）

同一个操作执行一次和执行十次，结果相同。

落地手段：给每条诏书一个 `edict_id`，重复提交直接忽略。
崇祯的反面案例：**重复抄家**。

---

## 存量 / 流量

借用会计的说法：

| | 含义 | 例子 |
|---|---|---|
| **存量** | 某一刻的余额 | 国库现有 120 万两 |
| **流量** | 一段时间内的进出 | 本季田赋收入 30 万两 |

崇祯的坑：
- 抄家是**存量**操作，不会自动变成持续收入
- 税率改了，**收入字段不会自动跟着变**
- 原因：税率和收入之间**没有公式边**

## 双向分录

记账的每一条都带方向：

```
debit（借/支出） / credit（贷/收入）  +  科目  +  金额（正数）
```

禁止模型直接填"余额 = 100 万"或"支出 = -5 万"。
崇祯的反面案例：**支出误记收入**。

---

## 上下文注入（Context Pack）

**记忆是注入的，不是回忆的。**

每回合由代码组装一个固定结构的小包：
- 固定种子集（玩家、当前场景、在场实体）
- 按相关度排序的有界记录

然后直接塞进 prompt。

关键点：模型看到的上下文是**已提交状态的确定性函数**，不是聊天窗口里剩下什么就用什么。

崇祯的做法是反的：靠超长上下文 + 摘要检索硬扛，所以会漂移。

---

## 封驳

中国古代制度：臣下可以把皇帝的诏令**封还驳回**，不予执行。

`[判读]` 在游戏里，这是把"校验失败"叙事化的天然外壳——
不是弹一个红框说"操作不合法"，而是呈上一封：
> "臣等谨驳：内帑现存银一十二万两，诏书所拨三十万两，无从筹措。"

---

## Function Calling / 工具调用

模型不直接输出文本答案，而是输出一个**结构化调用**：函数名 + 参数。

好处：参数有 schema，可校验；后端能可靠执行。
崇祯官方明说"输出准确的函数调用"来更新国库、派系、军队——说明其动作空间在代码侧是封闭的。

---

## IR（中间表示）

Intermediate Representation。把自然语言先转成一层结构化的中间形态，再交给下游处理。

在诏书场景：`诏书原文 → Edict IR（意图 + 参数 + 证据片段）→ 结算`。

好处：可校验、可打日志、可人工复核"模型是不是理解错了"。
